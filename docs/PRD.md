## 1. 项目概述与赛题匹配

### 1.1 一句话定位
让旅行中陌生人的思绪匿名漂流、彼此接住的系统：信可随机漂向远方，也可埋在某地等后来者发掘。不是社交网络、不是推荐平台，是"作品先于作者抵达"的慢媒介。

### 1.2 赛题匹配：制造一点意外
本次参赛赛道为 **"制造一点意外"**（反"更懂你"的算法，创造用户自己都没想到会遇见的东西）。本项目的契合逻辑：

- 当前世界越來越"懂你"——推荐系统不断把最符合口味的东西送到眼前，生活变方便也变可预测。
- 真正有意思的瞬间往往来自计划之外：误读的书、临时拐进的小路、与陌生人的偶然交谈。
- **本系统正是"反过来和算法玩一次"**：它不预测你想要什么，而是把一封陌生人的信，随机（或按地点偶然）送到你手里——一次**陌生人之间恰到好处的相遇**，一种**随机探索陌生思绪**的体验。
- 它不追求精准，只负责"打开新的可能"。这与赛题"技术能不能不只给答案，也负责打开新的可能 / 别把世界变得更确定"完全对齐。

### 1.3 核心循环
```
✍️ 创作 → 📮 留/投 → 🌍 旅行或埋藏 → 👤 拾取/发掘 → 📖 阅读
   → ✦共鸣 / 📝回信（独立作品）→ 原作者得知（非私信）
   → 继续旅行/再埋  └→ 回信者再创作
```

## 2. 我们要解决什么（问题与机会）

### 2.1 问题（Insight）
- **身份先于内容抵达**：社交平台上你发出的每句话先挂着"你是谁"，别人先看人再看话。
- **点赞失真**：一个赞混着真情共鸣、肌肉记忆、对"你这人"的追捧——它传递"被看见"，不传递"被理解"。
- **私域太窄、公域太吵**：熟人圈受众有限且同质；公共平台淹没在算法与表演里。
- **陌生人本可相遇却永不相遇**：同车、同站台的两个人，因"不认识"而终生不交换任何东西。

### 2.2 机会
- **慢媒介回流**：手账、明信片、写信复兴，反映对"非即时"的渴望。
- **技术已轻得足以承载**：定位、LLM 润色、PostGIS 地理发掘今天都能低成本实现"思绪的地理漂流"。
- **比赛语境**：10 天赛期 + 云服务器资源，足以把有灵魂的小想法做成高完成度 demo。

## 3. 产品是什么（系统概述）

- **匿名精神漂流系统**：用户写下一段思绪（文字 + 可选图/主题/音乐引用/AI 短诗），选择让其**漂向陌生人**或**埋于某地**。
- **双机制并存（一等公民）**：
  - **投递出去（Drift）**：入随机漂流池，被任意陌生人抽取。
  - **留在这里（Stay / 埋信）**：锚定当前位置，后来者"就地发掘"。
- **展示层匿名**：信只携 `地点·时间·天气`（+ 用户自选主题/图），不携可识别作者信息。
- **不要求对话**：回信是独立作品，不是私信。

---

## 4. 目标用户与角色（行为角色，非固定身份）

匿名性下，用户以**行为角色**参与，而非固定账号身份：
- **写信者**：旅途/漂泊中想"说点什么但不想被认出"的人。
- **发掘者**：到某地开启"就地发掘"，翻看曾埋于此的信。
- **漂流接收者**：随机收到漂来信的陌生人。
- **氛围用户**：不写只读，仅共鸣/收藏/留声。

> 注：系统保留账户（见 6.13），但角色由行为定义，展示层不暴露"这是谁"。

## 6. 功能需求（带优先级 · 规格层）

**P0 = 初赛必须 ｜ P1 = 初赛争取 ｜ P2 = 二期 / 延后**

### 6.1 匿名写信与投放（P0）
- 文字（≤ 800 字）。
- 图片：**1 张（明信片式），最多 3 张**，压缩存 URL。
- 主题皮肤使用默认「夏」；自选皮肤槽位属于 P1，仅装饰。
- 音乐引用（P1 选填）：专辑 + 歌曲 + 一句歌词。
- 落点：自动 `地点·时间·天气`，可改/可手动。
- **必选投递方式**：「留在这里」或「投递出去」。
- 提交入审（审核中 → 公开）。

### 6.2 AI 润色与短诗（P0，可关）
- 润色：保留原意，用户可选采纳。
- 短诗：从正文提取意象生成 ≤ 4 行，同屏展示。
- 失败时降级为纯手动写信，不影响主流程。

### 6.3 投递出去 · 随机漂流（P0）
- 读者「随机漂流」：抽一封 **非自己发、未读过** 的公开信。
- 展示：地点·时间·天气 + 正文 + 图 +（短诗）+（音乐引用）+ 叙事计数；无作者。
- 初赛纯随机；P1 可加同标签/同场景轻度加权（禁变推荐流）。

### 6.4 留在这里 · 地理埋信与就地发掘（P0）
- 埋信（P0）：选「留在这里」锚定位置（PostGIS geometry），入该地信库。
- 就地发掘（P0）：到某地按位置检索附近「留在这里」的信（半径可配，默认 ~1km）。
- 与随机漂流并列的核心机制，使同地陌生人跨越时间对话。
- 发掘到的信可「让它继续旅行」（转投漂流池，P2 可选）。

### 6.5 回信机制（P0）
- 读者「回以一封信」→ 进入写信流，新信预置 `parent_letter_id`（溯源），可引用原信一句（可选）。
- 回信是**独立信件**：写完同样选「留在这里 / 投递出去」。
- **告知原作者（非私信）**：回信发布后，原信 owner 收通知「你于 {地点} 写的那封信，收到一封回信 ✦」；点击可读这封**公开**回信。原作者不是回信的收件人，回信面向所有陌生人。
- **可达性边界**：通知仅对绑定了 device/账号的作者生效；纯过客（未绑定）所写的信收到回信时不主动通知，该回信照样公开，由后来者经 `parent` 溯源发现。
- 溯源：任何读者可读到回信并上溯原信（若公开），形成弱链接作品链。

### 6.6 共鸣与互动（P0 一键 ✦ · P1 短句）
- **✦ 共鸣（P0）**：一键 `resonance_count +1`，信获叙事展示「已被 N 个陌生人接住」。**不是点赞**，不展示谁。
- **共鸣短句（P1）**：可选附 ≤ 30 字「我也曾有过这样的时刻」，匿名存储，可聚成信下「共鸣墙」（匿名碎片，P2 展示）。
- **禁止**：点赞 / 评论 / 转发 / 关注。

### 6.7 音乐表达（P1）
- 引用式：用户填 `专辑名 + 歌曲名 + 一句歌词`（选填），信中以「此刻我循环着《专辑》的《歌》——『歌词一句』」呈现。
- 不生成、不上传音频，也不支持贴外部音乐链接（音频生成 / 上传 / 外链均延后，非初赛范围）。音乐概念在初赛阶段完全由「歌词引用」承载。

### 6.8 思绪标签（P1）
- 写信选 1–3 个预置标签；用于收信轻度匹配、聚合。

### 6.9 主题皮肤系统（P1）
- 「夏」默认皮肤；`theme` 字段解耦，新增主题仅加皮肤包。
- **永久绑定（D20）**：信件一旦选定皮肤即永久绑定该 `theme`，不因平台后续推出新主题而迁移或改写；不做季节归档/自动切换。

### 6.10 抄本收藏（P1）
- 读者可手动把喜欢的信收藏进个人「抄本」（Scripbook）；个人行为，不计入公开互动。可浏览/导出。

### 6.11 信件导出为图片（P1）
- 信件可渲染为图片（带主题皮肤、含正文/图/短诗/音乐引用/地点时间天气/叙事计数），**不含作者信息**。用户自存相册或自发社媒（用户自身行为，平台不代发）。

### 6.12 个人统计地图（P2）
- 不做单信轨迹；做**个人统计**：「我写下的信」地理分布 + 「我收到的信」来源地理分布（PostGIS 聚合）。仅自己可见，稍晚实现。

### 6.13 用户账户系统（P0）
- 账户存在：注册/登录（或设备绑定 + 可选账号），支撑跨设备、「我的信」、抄本、设置、删除、回信通知。
- 发布匿名：展示层永不暴露账户；`owner_user_id` 仅服务端管理用。

### 6.14 内容运营控制台（P1）
- 独立的后端管理控制台（Web 或 CLI），供运营/评审/开发者手动管理信池：预填充种子信、审核队列、下架、统计概览。
- 控制台账号与匿名用户体系隔离；不暴露作者给访客。
- 价值：解决「漂流池冷启动」，是 10 天高完成度 Demo 的运营抓手（具体种子信内容待定）。

## 7. 关键产品规则（实现不可违背）

以下规则是产品的"红线"，任何实现都必须遵守：

1. **匿名展示铁律**：信件展示层永不渲染头像/昵称/主页；读者不可达作者。
2. **不做社交度量**：不点赞、不关注、不推荐 Feed、不热榜、不积分排行榜。
3. **回信是独立作品，非私信**：原作者非回信收件人；回信面向所有陌生人。
4. **计数替代轨迹，不跨信排行**：只展示叙事计数（读/互动/回信/抄），不记录单信空间轨迹，不做跨信热度比较。
5. **生命周期默认永驻**：漂流/埋信默认永驻池无限重抽；`expire_at` 可空字段预留（默认 NULL=永驻），初赛不启用过期。
6. **皮肤永久绑定单信**：主题皮肤选定后不与信件分离，不做季节归档迁移。
7. **音乐引用式**：初赛仅「专辑+歌曲+歌词」引用，不生成/不上传/不链外音频。
8. **AI 是桥不是枪手**：润色/短诗保留原意，且可整体关闭不影响主流程。

## 8. 非功能性需求

### 8.1 匿名性与隐私
- 数据最小化：信件不存作者画像。
- 展示层匿名：永不渲染作者信息；读者不可达作者。
- 位置可控：可改/模糊城市级；发掘半径可配。
- 可删除：所有者下架自己信（含其回信链入口）。
- 导出图不含作者信息。

### 8.2 内容审核
- 发布前机审（关键词 + LLM 违规分类），违规不公开；举报入口；人工后台（P1）。
- 机审失效时默认**待审不公开**，不降级为直接公开。

### 8.3 部署与存储
- 云服务器：PostgreSQL + PostGIS；docker-compose 起 后端 + PG(PostGIS) +（可选）对象存储。
- **模块可降级**：地图 / 天气 / LLM / 审核任一失效，核心循环（写→漂→收→共鸣→再写）仍可跑。

### 8.4 性能
- 写 → 落池 < 2s；随机抽 < 1s；就地发掘 < 1s；计数自增廉价。
- 离线可写（P1）；多端一致。

## 9. 数据模型（实体规格 — 用于推导数据 / 接口契约）

> 本节给出实体与关键字段，足以推导前后端契约。**具体 API endpoint 定义不在本文范围**，由本模型派生。

| 实体 | 关键字段 | 说明 |
|---|---|---|
| User | id, auth, created_at | 匿名账户（发布匿名） |
| Letter | id, content, poem, images[url](1–3), theme, music_ref{album,song,lyrics}, location geometry, weather, created_at, tags[], delivery_mode(stay/drift), status, owner_user_id, parent_letter_id(可空,溯源), expire_at(可空,默认NULL=永驻), read_count, resonance_count, voice_count, reply_count, saved_count | 主体；计数替代轨迹 |
| ResonanceLog | letter_id, user_id, note(≤30,可空), time | 共鸣记录（匿名展示） |
| Scripbook | user_id, letter_id, added_at, note(可空) | 个人抄本收藏 |
| Notification | user_id, type(reply), letter_id, parent_letter_id, is_read | 回信告知原作者 |
| ThoughtTag | id, name, color | 预置标签 |
| Theme | id, name, assets, default? | 主题皮肤（夏默认，永久绑定） |
| AdminAccount | id, role, created_at | 内容运营控制台账号（与匿名用户隔离） |

**索引 / 关系提示**：location GiST；漂移池按 `status + delivery_mode`；发掘用 `ST_DWithin`；reply 按 `parent_letter_id`；Notification 按 `user_id + is_read`。

## 10. 技术约束与架构边界（高层 · 非路线图）

- **形态**：Flutter 跨平台 App（Android/iOS；Flutter Web 作演示兜底）。
- **存储**：PostgreSQL + PostGIS（地理扩展支撑就近发掘）。
- **后端**：轻量服务（FastAPI 或 Node）；ORM（SQLAlchemy / Prisma）。
- **模块边界**（职责划分，供契约设计参考）：
  ```
  [Flutter] ──REST──> [后端 API]
     ├─ 信服务（存取 / 漂流分发 / 地理发掘 ST_DWithin / 计数自增）
     ├─ 账户服务（匿名发布）
     ├─ 回信与通知服务（parent 溯源 + 原作者告知）
     ├─ 共鸣 / 抄本服务
     ├─ 主题 / 导出服务
     └─ AI / 位置天气 / 审核（均可降级）
              └─ [PostgreSQL + PostGIS]
  ```
- **第三方可降级原则**：地图 / 天气 API / LLM（润色·短诗·审核）/ 图片对象存储，任一不可用时不阻断核心循环。

## 11. 验收标准 / Definition of Done

**端到端双路径走通（双设备验证）**：
1. A 写信「留在这里」埋于 X 地 → B 到 X「就地发掘」读到，并共鸣、回信 → A 收到「有回信」通知并读到该公开回信。
2. C「投递出去」→ D 随机收到、拆封并读到。

抄本收藏、音乐/标签/自选皮肤与导出图片按 P1 单独验收，不阻塞 P0 双路径判定。

**P0 清单全部完成**：
- Flutter App 可运行（Android 优先，Web 可演示）。
- 匿名账户（发布剥离作者）。
- 写信：文 + 图(1–3) + 默认主题(夏) + AI 润色/短诗（AI 可关闭并降级为纯手动）。
- 双投递：留在这里 / 投递出去。
- 收信双入口：随机漂流 + 就地发掘（PostGIS）。
- ✦共鸣（一键）+ 回以一封信（独立信、留/投、溯源、告知原作者）。
- 叙事计数（读/互动/回信）；发布前机审 + 举报。
- PG + PostGIS + docker-compose；核心循环端到端。

**贯穿铁律**：全程无强制注册、无作者暴露、无点赞/关注/热榜。

## 13. 视觉设计指向（指向 token，不展开）

视觉实现以提供的 design tokens 为准，本文不定义具体色彩/字体/间距/动效：

- **`yorushika-design-tokens.json`** — 文学书信体系：和紙暖调 + 版画黒墨 + 朱点缀；无阴影，靠纸感与留白。
- **`natsu-tokens-v2.json`**（当前主方向）—「夏の手紙 v2」：夏日天空渐变 + 浮起的白纸 + 手写体内容 + 珊瑚色邮戳/邮票（配给制）；墨蓝正文、夏空蓝交互。

**关键视觉纪律（便于评审/实现对齐）**：

- Controlled Imperfection：不完美（轻微倾斜/偏移）只属于"内容物"，确定性种子 ±1.5–2° / ±4–6px。
- 珊瑚色配给制：仅用于邮戳/邮票/旅行标记，装饰图形不承载正文。
- 阳光黄永不作文字色。
- 衬线只活一处：仅歌词引用 / AI 短诗使用引用体。
- 手写体承载信件"温度层"；字体回落链中文优先（SC 主 JP 回退）。

## 附录：赛题要点（"制造一点意外" · 供评审对齐）

- 我们越來越"懂你"，生活变方便也变可预测；真正有意思的事常来自计划之外。
